**scml**
Le SCML (Structured Contract Markup Language) est un interpréteur XML minimaliste pour contrats structurés. Il rend programmables les fichiers Markdown (.md), qui constituent le format dominant de documentation et de pilotage utilisé par les agents comme Claude Code. Les balises XML sont injectées dans les commentaires Markdown : elles demeurent invisibles après rendu tout en servant de points d’ancrage exécutables pour l’interpréteur. L’agent qui traite un contrat SCML est forcé de suivre une démarche définie explicitement. Une tâche n’est considérée comme terminée que lorsque chaque élément du contrat est respecté, ce qui empêche l’agent de sortir de la portée de la requête.
Le parseur transforme un document SCML en un modèle Go structuré (`Contract`) qui expose plusieurs vues : un schéma de référence pour la validation, un schéma JSON destiné aux sorties structurées du LLM, les métadonnées de validation pour les listes de fichiers, et une vue de politique d’accès. Il prend en charge la résolution de constantes (`${KEY}`), les dépendances entre sections (`depends-on`), les sections imbriquées en routes hiérarchiques, et les importations de contrats externes. Pour les sections de type `file-list` avec politique `write`, le parseur vérifie l’existence réelle des fichiers référencés sur disque.

**gate**
Gate constitue le mécanisme de validation déterministe de PromptControl. Son rôle est de vérifier qu’un contrat produit par un LLM respecte exactement la structure définie par le SCML. Le validateur compare récursivement le JSON retourné à la représentation de référence générée par le parseur. Il vérifie l’intégrité des sections, des champs, des métadonnées et des dépendances attendues. Les éléments obligatoires doivent être présents, correctement remplis et conformes à la définition du contrat.
Pour les listes de fichiers, gate vérifie également l’existence des ressources sur disque. Cette approche retourne une liste exacte et triée des éléments manquants ou invalides plutôt qu’un simple échec binaire. Le modèle peut alors corriger les parties concernées.

De cette manière, gate agit comme une passerelle entre le comportement probabiliste des LLMs et les exigences déterministes des systèmes logiciels. Son rôle n’est pas de faire confiance au modèle, mais d’imposer la conformité structurelle avant toute exécution. Un plan peut contenir une section « fichiers à modifier » que le LLM est obligé de remplir. Toute tentative d’écriture à l’extérieur du contrat peut être interceptée et bloquée. Le contrôle est assuré par le logiciel plutôt que par le modèle, ce qui rend les mécanismes de contournement considérablement plus difficiles. Cette sécurité préventive externe au LLM travaille conjointement avec les CLAUDELETs dans le concept de coffrage pour code généré.

**forge**
Forge est l’orchestrateur qui relie scml et gate en une abstraction de flux de travail uni. Un appelant fournit un chemin de contrat et un client LLM ; forge prend en charge l’intégralité du processus. Il parse le SCML, construit le prompt système avec un instantané de la base de code, envoie le schéma JSON au modèle, puis valide chaque réponse via gate.
Lorsque la validation échoue, forge fusionne intelligemment les valeurs manquantes dans l’arbre de travail et relance un appel ciblé sur les lacunes identifiées. La boucle de retry préserve les valeurs déjà validées et ne demande au modèle de corriger que les champs ou fichiers manquants. Une processus iteratif  se rapprochant de l'etat d'un contrat conforme s'appel le : forgeagle de contrat.
Ce mécanisme permet d’obtenir un contrat JSON complet et conforme à partir d’un document SCML, sans que l’appelant n’ait besoin de connaître les détails du parseur ou du validateur.
